2. إدارة المحتوى

  • يتحكم فريق المجمع في محتوى الموقع بالكامل عبر لوحة التحكم دون أي تدخل تقني.
  • يمكن حفظ النشاط كمسوّدة ثم نشره لاحقاً — لا يظهر على الموقع العام حتى يُنشر.
  • التغييرات المنشورة تنعكس فوراً على الموقع.

3. بيئتا التشغيل (Staging و Production)

يُنشر المشروع على بيئتين منفصلتين تماماً لضمان جودة الإصدارات وعدم تأثُّر المستخدمين بأي تغييرات قبل اعتمادها:

البيئةالنطاقالغرضالجمهور
بيئة التجربة (Staging)staging.example.saاختبار التحديثات والمراجعة الداخلية قبل النشر الرسمي — نسخة مطابقة للإنتاج ببيانات اختباريةفريق المجمع التقني والمحتوى
بيئة الإنتاج (Production)example.saالموقع الفعلي المُتاح للعموم — يستقبل الزيارات الحقيقيةالزوار + فريق المجمع
  • كل بيئة معزولة بقاعدة بيانات وتخزين ومتغيرات بيئة (Environment Variables) مستقلة تماماً.
  • لا يُنشر أي تغيير على الإنتاج قبل اعتماده على بيئة التجربة.

4. الاستضافة والأمان والإتاحة العالية (High Availability)

صُمِّمت بنية الإنتاج لتكون عالية الإتاحة (HA) مبنيةً على Kubernetes (Oracle OKE)، بحيث لا يتسبب تعطُّل أي مكوِّن منفرد في توقُّف الموقع:

  • يعمل التطبيق داخل حاويات Docker تُدار بواسطة Kubernetes (Oracle OKE).
  • NGINX Ingress Controller: نقطة الدخول الوحيدة المكشوفة للإنترنت داخل الـ cluster؛ يستقبل حركة HTTPS ويوزِّعها على pods التطبيق ويُجري فحوصات صحة دورية لاستبعاد أي pod متعطِّل تلقائياً.
  • تعدُّد نسخ التطبيق (Replicas): نسختان على الأقل من pods التطبيق تعملان في وضع Active-Active داخل K8s Deployment مع استراتيجية RollingUpdate — لا يُزال أي pod قديم إلا بعد أن يصبح الجديد جاهزاً.
  • فحوصات الصحة (Health Probes): كل pod يكشف مسارَين للـ K8s:
    • /api/health/live — Liveness Probe: يتحقق من أن العملية حية؛ يُعيد K8s تشغيل الـ pod إذا فشل.
    • /api/health/ready — Readiness Probe: يتحقق من اتصال قاعدة البيانات؛ يُوقف K8s توجيه الطلبات إلى الـ pod حتى ينجح.
  • قاعدة البيانات: OCI Database with PostgreSQL كخدمة مُدارة خارج الـ cluster — تشمل نسخاً احتياطية يومية مدمجة وتحويلاً تلقائياً (Automatic Failover) عند التعطُّل.
  • نسخ احتياطي يومي (Backups): تُدار بالكامل من Azure — نسخ احتياطية مشفَّرة تُحفَظ 30 يوماً على الأقل.
  • عزل البيئات: لكل بيئة (staging/production) namespace Kubernetes مستقل مع secrets وconfigmap خاصَّين بها.
  • مراقبة (Monitoring): مراقبة مستمرة لزمن الاستجابة، استهلاك الموارد، وحالة الـ pods مع تنبيهات فورية.
  • لوحة التحكم محمية بمصادقة قوية ومستبعدة من محركات البحث.

هدف مستوى الخدمة (SLA): إتاحة 99.9% شهرياً، مع زمن استرجاع (RTO) أقل من 15 دقيقة وزمن فقد بيانات (RPO) أقل من 5 دقائق.

5.أ. بناء الحاويات (Docker)

يُبنى التطبيق كصورة Docker متعددة المراحل (Multi-Stage Build) لتقليل الحجم النهائي وضمان عدم تسريب أدوات التطوير في بيئة الإنتاج:

المرحلةالغرض
baseصورة node:20-alpine الأساسية مع libc6-compat
depsتثبيت حزم npm (npm ci) ونسخ ملفات Prisma لتوليد الـ client
builderاستقبال NEXT_PUBLIC_* كـ build-args وتشغيل prisma generate ثم npm run build — ينتج standalone output في .next/standalone/
runnerصورة نهائية خفيفة تحتوي فقط على .next/standalone والأصول الثابتة — تعمل بمستخدم غير root (nextjs:1001)
  • Standalone Output: يُفعَّل في next.config.ts بـ output: "standalone" — يُنتج server.js منفرداً لا يحتاج node_modules الكاملة عند التشغيل.
  • NEXT_PUBLIC_* build-time baking: المتغيرات العامة (مثل NEXT_PUBLIC_FRONTEND_URL) تُحقن وقت البناء عبر --build-arg، لذا تُبنى صورة منفصلة لكل بيئة (staging ≠ production).

6. المنافذ المفتوحة واتجاه حركة البيانات

في بنية Kubernetes، نقطة الدخول الوحيدة للإنترنت هي NGINX Ingress Controller الذي يحمل عنوان IP عاماً واحداً. جميع المنافذ الداخلية تبقى داخل الـ cluster:

المنفذالبروتوكولالاتجاهالغرض
80HTTPوارد — NGINX Ingress فقطإعادة التوجيه التلقائي إلى HTTPS
443HTTPSوارد — NGINX Ingress فقطحركة المرور العامة؛ TLS يُنهى عند الـ Ingress
3000HTTPداخلي — داخل الـ cluster فقطمنفذ التطبيق (Next.js) — لا يُكشف خارجياً
5432TCPصادر من الـ cluster إلى OCI Database with PostgreSQLاتصال التطبيق بقاعدة البيانات الخارجية المُدارة
كل المنافذ—صادرسحب صور Docker من OCIR، تحديثات الحزم، اتصالات SSL

7. متطلبات الوصول والإعداد

لإتمام عملية الإعداد والنشر، يحتاج الفريق التقني إلى ما يلي من المجمع:

  • اشتراك Azure نشط مع صلاحية إنشاء موارد (Contributor أو Owner).
  • مشروع Azure DevOps مع صلاحية إنشاء Pipelines وVariable Groups وService Connections.
  • اسمَا نطاق الإنتاج والتجربة — سيزوِّد الفريق التقني المجمعَ بعنوان IP الـ Ingress Controller بعد اكتمال إعداد الـ cluster، ويتولى المجمع توجيه A Record كل نطاق إلى هذا العنوان من لوحة إدارة DNS الخاصة بهم.
  • ملفات شهادة SSL لكلا النطاقَين (ملف الشهادة، المفتاح الخاص، وسلسلة CA) — سيستلمها الفريق التقني ويثبِّتها كـ Kubernetes Secret على الـ Ingress Controller.
  • إعدادات SMTP (مضيف، منفذ، بيانات المصادقة) لإرسال رسائل OTP وإعادة تعيين كلمة المرور.
لا يلزم الوصول المباشر إلى خوادم VPS — إدارة OKE تتم من Azure Portal أو Azure CLI أو عبر Azure DevOps Pipelines.

8. النطاقات وشهادات SSL

المهمةالمسؤولالتفاصيل

9. سير النشر والتسليم (Azure DevOps CI/CD)

النشر مؤتمَت بالكامل عبر Azure DevOps Pipelines — لا يتطلب أي تدخل يدوي على الخوادم:

  • الكود مخزَّن في مستودع Git مع فرعَين رئيسيَّين: main للإنتاج وdevelop للتجربة.
  • دورة النشر: أي تحديث يُنشر أولاً على بيئة التجربة ← يُراجَع ويُعتمَد من فريق المجمع ← ثم يُدمج في main وينشر على الإنتاج تلقائياً.

خطوات الـ Pipeline عند كل نشر

#الخطوةالتفاصيل
1بناء صورة Dockerيُشغَّل docker build مع تمرير NEXT_PUBLIC_* كـ build-args مأخوذة من Variable Group البيئة — تُنتج صورة مستقلة لكل بيئة
2رفع الصورة إلى OCIRdocker push إلى Oracle Cloud Infrastructure Registry بوسم يتضمن رقم البناء
3إنشاء Kubernetes Secretيُنشأ أو يُحدَّث secret يحتوي DATABASE_URL، JWT_SECRET، SMTP، بيانات الأدمن — القيم تأتي من ADO Secret Variables ولا تُسجَّل في أي ملف
4تطبيق الـ overlaykubectl apply -k overlays/staging/ أو overlays/production/ — يُنشئ namespace ويُطبِّق ConfigMap وService وIngress
5تشغيل ترحيل قاعدة البياناتيُحذف Job القديم ثم يُطبَّق migration-job.yaml الذي يُشغِّل prisma migrate deploy — Pipeline يتوقف هنا في حال الفشل ولا ينتقل للنشر
6انتظار اكتمال الترحيلkubectl wait --for=condition=complete --timeout=300s job/ksgaal-activity-map-migrate
7نشر التطبيقkubectl apply -f base/deployment.yaml — يُطبِّق RollingUpdate فلا يُزال pod قديم إلا بعد جاهزية الجديد
8انتظار اكتمال الـ rolloutkubectl rollout status deployment/ksgaal-activity-map --timeout=300s — يفشل الـ pipeline إذا لم تكتمل خلال 5 دقائق
9اختبار دخاني (Smoke test)التحقق من /api/health/live و/api/health/ready — كلاهما يجب أن يُعيد HTTP 200
جميع الأسرار (كلمات المرور، مفاتيح JWT، بيانات قاعدة البيانات) محفوظة في Azure DevOps Secret Variable Groups ولا تُخزَّن في ملفات الكود أو سجلات الـ pipeline.

11. المخططات البيانية

أ. بنية Kubernetes في وقت التشغيل

يوضِّح المخطط مكونات الـ cluster الكاملة: المستخدمون ← DNS ← NGINX Ingress ← Service ← Pods ← PostgreSQL + SMTP. يُبيِّن أيضاً ConfigMap وSecret وPrisma Migration Job.

ب. تدفق طلب المستخدم العام (Public Request Flow)

مخطط تسلسلي يُتابع طلب HTTPS من الزائر العام حتى استجابة الصفحة، مع منطق Cache Hit / Cache Miss لبيانات الكرة الأرضية.

ج. تدفق مصادقة المدير ولوحة التحكم (Admin Auth Flow)

مخطط تسلسلي يُوضِّح خطوات تسجيل الدخول: التحقق من كلمة المرور ← إرسال OTP عبر SMTP ← التحقق من OTP ← إنشاء جلسة آمنة ← الوصول إلى لوحة التحكم.

د. خط أنابيب النشر التلقائي (Azure DevOps CI/CD Pipeline)

يُبيِّن المخطط الرحلة الكاملة من لحظة دفع الكود حتى وصوله إلى الـ cluster: التحقق من الكود ← بناء صورة Docker ← رفعها إلى OCIR ← نشرها على K8s ← تشغيل Migration Job ← Rolling Update.
