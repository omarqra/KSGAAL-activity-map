# سياسة النسخ الاحتياطي والاستعادة — Backup & Restore Policy

> معالجة الملاحظة 6 في تقرير مراجعة الجودة التقنية.

## السياسة (Policy)

| البند | القيمة |
|------|--------|
| المعدّل (Frequency) | نسخة احتياطية يومية تلقائية |
| مدّة الاحتفاظ (Retention) | آخر 30 نسخة (قابلة للضبط عبر `BACKUP_RETENTION`) |
| الموقع (Location) | مجلد `backups/` — يجب وضعه على وحدة تخزين منفصلة عن خادم قاعدة البيانات |
| الصيغة (Format) | `pg_dump` بصيغة custom (`-Fc`) — مضغوطة وقابلة للاستعادة عبر `pg_restore` |
| RPO (هدف نقطة الاستعادة) | ≤ 24 ساعة |
| RTO (هدف زمن الاستعادة) | ≤ 4 ساعات |

## أخذ نسخة احتياطية (Backup)

```bash
node scripts/backup-db.mjs
```

يتطلب وجود `pg_dump` ضمن PATH ومتغير البيئة `DATABASE_URL`.

ينتج ملفاً باسم `backups/backup-YYYYMMDD-HHmmss.dump` (توقيت UTC)، ثم يحذف النسخ الأقدم تلقائياً بحيث يبقى آخر 30 نسخة.

### الجدولة اليومية (Scheduling)

- **Linux / cron** — تشغيل يومي الساعة 2 فجراً:
  ```cron
  0 2 * * * cd /app && node scripts/backup-db.mjs >> /var/log/db-backup.log 2>&1
  ```
- **Windows Task Scheduler** — مهمة يومية تشغّل الأمر نفسه.
- **Docker Compose** — حاوية مرافقة (sidecar) أو cron على المضيف يشغّل الأمر داخل حاوية التطبيق.

## الاستعادة (Restore)

> إجراء يدوي موثّق ينفّذه فريق التشغيل. يُنصح بالاستعادة إلى قاعدة بيانات مؤقتة أولاً والتحقق قبل استبدال الإنتاج.

1. حدّد ملف النسخة المطلوب من `backups/`.
2. استعد إلى قاعدة بيانات (موجودة وفارغة):
   ```bash
   pg_restore --clean --if-exists --no-owner --no-privileges \
     --dbname "$DATABASE_URL" backups/backup-YYYYMMDD-HHmmss.dump
   ```
3. تحقّق من سلامة البيانات بعد الاستعادة:
   - عدد الصفوف في الجداول الأساسية (`Activity`, `Country`, `Organization`, `User`).
   - تسجيل الدخول إلى لوحة التحكم وظهور الأنشطة على الموقع العام.
4. وثّق زمن الاستعادة ضمن سجل التشغيل للتأكد من تحقيق RTO.

## التحقق الدوري (Verification)

- اختبار استعادة شهري على بيئة منفصلة للتأكد من صلاحية النسخ.
- مراقبة نجاح مهمة النسخ اليومية (تنبيه عند الفشل).
